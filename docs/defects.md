# ДЗ6+7 — четыре дефекта исходной заготовки

## 1. Разные конфигурации смешивались в одном запуске

В `src/sweep.py` цикл кандидатов был внутри одного дочернего run. Параметры
MLflow неизменяемы; условие «логировать, только если параметров ещё нет»
оставляло параметры первой модели рядом с метриками последующих.
Исправление: каждый кандидат получает отдельный дочерний run внутри
одного родительского sweep. Все шесть конфигураций завершились отдельно; таблица и версии записаны в отчётах ниже.

## 2. Файлы моделей терялись при замене контейнера

Объявленного имени тома недостаточно: сервер писал `/mlartifacts` во
внутреннюю файловую систему контейнера. Исправление — подключить
`artifacts:/mlartifacts` к сервису MLflow. PostgreSQL уже использует свой
постоянный том. Проверка создаёт probe-файл, пересоздаёт только сервис
MLflow и сверяет SHA-256 скачанного файла; файл с тем же SHA-256 восстановлен после пересоздания.

## 3. У запусков отсутствовали версии train и val

Функция provenance вычисляла SHA-256 файлов, но sweep отбрасывал ключи
`data_*`. Исправление — передавать все версии каждому кандидату. Имя
базы и commit Hugging Face закреплены; токенизация сохраняет ту же
ревизию. Полный индекс исходных вопросов связан с train.pt по всем id.

## 4. Регистрация обходила порог по ошибке

Готовая функция gate проверяла завершённость, конечность чисел и отношение
final/base loss, но promote её не вызывал. Отношение только вычислялось,
а в реестр записывалась отметка «passed». Теперь gate вызывается до первой
записи в реестр. Отрицательная проверка порога выполняется отдельно.
Alias candidate означает прохождение этой проверки по loss; champion
назначается только после отдельной проверки качества ответов.
