# Личный планировщик — сервис в Kubernetes

ДЗ11: сервис развёрнут в настоящем локальном Kubernetes. Проверены прогрев, обновление и откат, распределение запросов и автоматическое добавление реплик. Вычислитель работает на процессоре и явно возвращает `backend_mode=simulated`. Это разрешённый основной вариант задания; качество языковой модели здесь не оценивается.

## Где находятся файлы

`src/cluster_api.py` — обработчик, прогрев, очередь, вычисления и метрики. `service.py --backend-mode simulated` включает этот режим. `infra/helm/planner/` — шаблоны контейнеров и сетевых входов; `values.yaml` задаёт версии и ограничения. `infra/monitoring/` — Prometheus, правила тревог и экспорт Grafana. `scripts/hw11/` и `tests/hw11/` запускают опыты и проверки. `results/hw11/` содержит исходные журналы, включая неудачные контрольные запуски. В CSV поле `analysis_included` отделяет сопоставимые измерения от сохранённых контрольных серий.

История диалога передаётся целиком в каждом запросе. Маленькие неизменяемые файлы версий A и B хранятся в ConfigMap и проверяются по SHA-256. После замены контейнера загружается та же версия, история диалога сохраняется у клиента.

## Воспроизведение

Нужны Docker с 8 CPU и примерно 8 GiB памяти, Python 3.12, `uv` и `kubectl`. В использованном стенде: Docker Desktop 29.2.0, Kubernetes 1.34.0, kind 0.30.0 и Helm 3.19.0. Точные версии и контрольные суммы: [среда](results/hw11/versions.json), [образы](results/hw11/image-ids.json), [зависимости с хешами](requirements-k8s.txt). Весов модели в образе нет.

```sh
python3 scripts/hw11/install_tools.py
sh scripts/hw11/setup.sh
make k8s-status
make k8s-smoke
```

Установка создаёт отдельный кластер `mlops-hw11` и локальный `notes/work/hw11/kubeconfig`. Helm и kind устанавливаются в `notes/work/hw11/tools/` из официальных источников с проверкой SHA. Для инструментов анализа:

```sh
uv sync --frozen
```

Сохранённые доказательства проверяются без повторной нагрузки:

```sh
make k8s-evidence
.venv/bin/python scripts/hw11/verify_results.py
.venv/bin/python scripts/hw11/report.py
```

`k8s-evidence` выводит сводку сохранённого журнала. Для нового выполнения пяти проверок и сравнения нагрузки используйте отдельные каталоги. Эти команды меняют только учебный кластер и занимают несколько минут и более получаса соответственно:

```sh
make k8s-test
python3 scripts/hw11/run_balance.py --out notes/work/hw11/repeat-balance
```

Каждый новый каталог сравнения должен быть пустым. Генератор распределяет отправку по монотонным часам; плановое и фактическое время сохраняются. Начальные кеши очищаются. Перед серией B устанавливаются две прогретые реплики, стоимость попадания/промаха 5/80 мс процессора, очередь 32 и одно вычисление на реплику; автоматическое масштабирование отключается. Итоговый исходник собирает V3; сохранённая основная серия B выполнена на зафиксированной V2, её идентификатор и параметры находятся в данных опыта. Исторические данные при повторении не переписываются.

Для нового опыта масштабирования откройте перенаправление Prometheus в отдельном терминале и оставьте его работать:

```sh
kubectl --kubeconfig notes/work/hw11/kubeconfig -n mlops-hw11 port-forward svc/prometheus 19090:9090 --address 127.0.0.1
```

```sh
python3 scripts/hw11/run_autoscale.py --out notes/work/hw11/repeat-autoscale
python3 scripts/hw11/cohort.py
```

В опыте C обе стоимости вычисления равны 80 мс CPU, HPA использует запрос ресурсов 100m и порог 65%, минимум 2, максимум 3. Очереди и отказы ожидаются и сохраняются. Для Grafana:

```sh
kubectl --kubeconfig notes/work/hw11/kubeconfig -n mlops-hw11 port-forward svc/grafana 13000:3000 --address 127.0.0.1
```

Откройте `http://127.0.0.1:13000`; экспорт панелей находится в `infra/monitoring/dashboard.json`. Метрики хранятся два часа; исходные журналы в Git доступны независимо от этого срока.

## Размер и удаление

На Pod: CPU 100m/1, память 64/192 MiB. Prometheus ограничен двумя часами и 128 MB метрик, томом 256 MiB; Grafana — 64 MiB; каждый клиент — 64 MiB временного тома. Размер файлов выделенного узла около 2.5 GiB на момент замера: [измерения](results/hw11/storage.json). Это оценка собственного узла, а не сумма всех образов пользователя.

```sh
sh scripts/hw11/cleanup.sh
```

Команда удаляет только kind-кластер `mlops-hw11`. Образы локального Docker удаляются отдельно после проверки их использования. Лекции, окружение, kubeconfig, веса, голос и видео в Git не включены. Видеофайл передаётся отдельно; характеристики и проверка окончания — `docs/hw11/video-quality.json`.

Измерения относятся к управляемому имитатору на одном узле ARM64. Они не доказывают ускорение настоящей модели или устойчивость при потере узла. В отчёте разобраны цена локального кеша и случай Anthropic из лекции 11. [Описание выпуска модели и запуска без Kubernetes](docs/hw8910-project.md) сохранено отдельно; прежние команды и исходный режим API продолжают работать. Их 20 быстрых проверок [прошли](results/hw11/regression-checks.log), отпечаток преподавательских тестов `09bd65e6b886`.
